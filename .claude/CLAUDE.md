# MMFFDev Colour Picker

macOS colour picker app (MMFFDev Colour 3). The source is at the repository root; the two earlier apps were removed on 2026-10-02 and live only in git history. Build: `./build.sh` (compiles, runs the self-test, installs); installers: `./make_dmg.sh`, `./make_pkg.sh`. Day to day, open `Colorgain.xcodeproj` at the root in Xcode and Cmd+R: it builds a real signed bundle (Info.plist, icon, Sparkle, the helper, the commit stamped) into DerivedData and runs it, rebuilding only what changed; the installed app still comes from `./build.sh`. The project is generated from `project.yml` by XcodeGen and committed: after adding or removing a `.swift` file, run `xcodegen` at the root and commit the project with the file. `Package.swift` stays the definition `build.sh` compiles. To see the app as a brand-new user, launch it with `--new-user` (in Xcode: Product ▸ Scheme ▸ Edit Scheme ▸ Run ▸ Arguments, tick it for the run) or run `tools/open.sh new` for the installed app (a throwaway home, never your data; add `permissions` to make macOS ask again); `tools/open.sh me` opens it as you. Xcode's Cmd+R copy is signed with the Developer ID like the installed one, so permissions and chosen folders hold between builds; the scheme carries `--new-user`, `--classic` and `--self-test` unticked under Edit Scheme ▸ Run ▸ Arguments.

## Two build targets

Since 2026-10-06 the app ships two ways from the same sources. Know which one a branch is for before touching anything in the second list.

The Store build cannot carry: Sparkle (`main.swift`, `Package.swift`, the `SU*` keys in `Info.plist`), the Adobe root helper (`AdobeHelper.swift`, `helper/`, the LaunchDaemons plist), `runAsAdministrator` and the ACL unlock in `Helpers.swift` and `AdobeHelper.swift`, git push from the design pack, and `afplay`. Every remembered folder (`syncFolder`, `projectsFolder`, `appHome`, catalogue entries, project folders) must be a security-scoped bookmark, not a path. Press profiles come from ColorSync's installed-profile list, not folder scans. The backlog for this is in Vector under OB-88 Mac App Store Edition (themes TH-284 Sandbox And Store Build, TH-285 Store Purchases And Editions, TH-286 Store Submission); read it before any Store work. The footer of a Store build reads "AS Release" so a Store copy can be told from a direct one.

Keep the direct-download build working on its branches. A change that only serves the sandbox goes behind a build flag or stays on `osx-appstore-build`.

Since 2026-10-07 the app is called **Colorgain**, spelled exactly so: one word, capital C, American "Color". Every new piece of user-facing text says Colorgain. "MMFFDev Colour 3" is the old name; it survives only where renaming is a migration (the bundle and executable names, the Application Support folder, the bundle identifier, the Sparkle feed, the installers, the Store product identifiers) and goes when the rename feature in Vector is done. ## Build after every commit: both editions

Two Xcode projects sit at the root, both generated by XcodeGen and committed: `Colorgain.xcodeproj` is the direct download and `Colorgain Store.xcodeproj` is the Store edition (its spec is `appstore/project.yml`). Open either, press Run, and that edition opens; never open `Package.swift` in Xcode, which runs a bare binary that cannot be signed, relaunched or sandboxed. A permission that needs a restart does not relaunch under the debugger: the app says to run again instead. Since 2026-10-09 the old setup assistant (the wizard, `SetupAssistant`) no longer runs at launch: a first open goes straight to the Studio window, which opens on the startup splash (`StudioSplash`, the lighthouse) because the catalogue has no structure yet, and the splash's Set marks the setup done. The wizard stays on the app menu only. `./build.sh` installs the direct download and opens it on the Studio window (`OPEN=0` to skip); `./make_appstore.sh` installs the Store edition as `/Applications/MMFFDev - Colorgain.app` and opens it as a brand-new user on the Studio window (`COLORGAIN_OPEN=0` to skip). So what Rick sees after every build, from either script or from Cmd+R in either Xcode project, is Colorgain's own setup and window, never the old window. Run both after a commit that touches Swift. In Xcode the Store project's default scheme, Colorgain, also runs as a new user; the Colorgain As Me scheme opens the Store container as Rick. The main window has not been redesigned yet: once setup is done the app looks like MMFFDev Colour 3, and that is current code, not an old build. The footer says which build is running.


After every commit, run `./build.sh` so the installed app is the last commit. Commit first, then build: the build stamps the commit's short hash into the app, and the window's footer shows it at the bottom right as "Release v3.0  3f48079". A "+" after the hash means the build was made with uncommitted Swift changes. If Rick cannot see a change, compare that hash with `git log -1` before anything else.

## The Studio window (the redesign of the app itself)

`StudioWindow.swift` is the main window on Colorgain's own grid (`Design.App`): header, library rail, context rail, page, history rail, footer, all placed by frame and drawn in the ten text styles. Since 2026-10-08 it is the window the app opens, from every path: launch, the setup's end, a relaunch. The old window opens only with `--classic` (`tools/open.sh classic`) and is kept for the pages not yet redrawn. `--palettes` opens on the palettes view, `--palette "<name>"` on that palette, `--project "<name>"` on that member, and `--settings`, `--schema`, `--shortcuts`, `--halo`, `--tags`, `--lab`, `--contrast` or `--projects` on those views. The backslash key draws Master Inner, the grid, over the window. `--splash` opens the splash that sets up the work (TH-299) over the whole window: `StudioSplash.swift` holds the sections on the right, `SplashTree.swift` the tree on the left that the answers build as they are given (the toy to rename, add to and take from until Set), `SplashBuild.swift` the `SplashDraft` the answers fill and what it builds, `Lighthouse.swift` the picture (SceneKit, ported from the motion study in `design/lighthouse-demo`, the spiral tower; `--lighthouse-up` raises the whole tower at launch for framing it); it opens by itself on a catalogue with no collections, `--no-splash` keeps it away, and `--splash-loop`, or `defaults write ~/Library/Preferences/com.mmffdev.mmffdevcolour3 splashLoop -bool YES` until deleted, keeps the app in it as a design loop: every launch opens on it and Set starts it again without writing; `--splash-filled [n]` beside it opens at section n (the last by default) with every answer given, two collections and three streams of groups, for the scrolling pane and the bands. The tree bands the nodes the section in view is working on, a colour per block from `SplashTreeView.palette`, the same colour in a square before the block's cells; sections tell the tree through `marks`. The wheel never changes a section: only the buttons and the keys do, and a Choices section's blocks scroll in a pane of their own. The catalogue the app opens is the `currentCatalogue` default in that file; a name not in the registry at the app home (`catalogues.json`, on Rick's Mac in `~/Desktop/Colorgain Data`) falls back to the first listed. Always name the direct app's defaults by path, as above: both editions share the bundle identifier, so once the Store edition has run, `defaults write com.mmffdev.mmffdevcolour3 …` lands in its sandbox container (`~/Library/Containers/com.mmffdev.mmffdevcolour3/…`) and the direct app never sees it; `plutil -p` on each file shows which is which. Built 2026-10-08 for the library and palettes views only; Lab, Contrast and the palette page's options still live in the old window.

## What the product is

A full enterprise colour management and proofing system for 2D, 3D, video, graphic design and print. Hex is never the primary promise. The definition, the master colour design and the reasoning are in `COLOUR-MANAGEMENT.md` at the repository root: read it before any work on colour. The ideas list is `scratch.md`.

## The catalogue is one structure file and its assets (since 2026-10-09, branch catalogue-file)

`<Name>.colcat` holds the whole structure and no payload: collections with their Master Templates, levels between, members with their own schemas and their groups' folders, templates, tags, tombstones, and a link to every asset by id, kind and path. Everything with content is an asset file, ".col" and three letters: `.colpal` a palette, `.coltyp` a typography palette, `.colinf` a member's information pack, `.colswa` the Library's loose colours, `.colprf` its profiles, `.colhis` the history, `.colshr` a share. Every asset says its catalogue and its member. Folders follow the structure (`<Collection>/[<Group>/]<Member>/<group folders>`, `Library/Palettes|Typography|Swatches|Profiles`); there are no per-level files and no Templates folder. A catalogue may hold no collection; the first member made brings the first one back. `CatalogueTree.read` matches folders to the structure by name, then by the assets inside them, then a folder gone beside one come as a rename; what is left over is taken in (a member, or a collection at the root), what is still missing is gone, and the load is marked dirty so the structure file catches up. `CatalogueTree.write` settles folders and files by id and bins what the app listed and no longer has. Version 2 (`.colcatalogue` v2, `.colcollection`, `.colworkgroup`, `.colassets`, `.coltemplate`, `.colpalette`) comes across in place through `LegacyTree` and `Migration` after a byte-for-byte backup beside the catalogue; version 1 as before. A share is a small catalogue of its own cut from the structure, zipped with a manifest of SHA-256s and the place the subject came from, which the import offers first. `--bring-across <folder>` brings a copy across from the command line. Never write the version 1 or 2 shapes again. The self-test's "the tree on disk", "bringing an earlier layout across" and "sharing" sections are the proof to re-run.

## Type scale

`TextSize` in Helpers.swift is the only source of font sizes for UI text: `body` 13 for anything read (notes, names, fields, controls), `caption` 11 for labels over fields and captions, `title` 20 for a page title. Never below 11. Text painted inside swatch tiles is sized to fit and is the one exception. Every UI label starts with a capital.
