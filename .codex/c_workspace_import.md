# Import workspace

Right-clicking a Library asset bucket offers its specific Import action. Connected Palettes, Images and Photographs actions open `BucketIntakeInfoPane` in RailInfo without changing the current page. Destination is a grouped dropdown of valid My Library and unlocked client/product buckets, initially set to the clicked bucket. The source chooser accepts multiple files and lists every selected filename below it. Copy/Move/Reference and Add act on that selection and the currently chosen destination. Other setup types remain visible but disabled until their adapters are connected. The context menu does not write files by itself. The Header Import route remains a separate, general-purpose workspace and is never entered by these context actions.


## Image intake

StudioWindow.beginImageIntake opens the shared import composition: a source-folder tree in Rail 1, selected image previews in the viewport, and WorkspaceImageDestinationPane in Rail 2. Rail 1 groups common macOS folders and internal, external, and network drives; the group is the darkest `#1F2933` row, with each folder level lighter through the ten-step drive palette. Rail 2 has three open sections: Client Tree, My Library, and Custom Folders. Their WorkspaceBranchTree rows retain live node ordering and colours; client and My Library branches use ten-step charcoal and house-yellow depth palettes, while Custom Folders uses the drive palette. Copy, Move, and Reference are equal-width buttons above the destination sections, followed by a note naming the active catalogue and explaining the selected method. A full-width Import button follows the trees. Copy and Move write to the selected physical folder; Reference leaves the source in place. An import validates readable images before the file-manager transaction changes bytes or indexes. Catalogue destinations and custom disk destinations are recorded in the active .colcat; My Library destinations use my_library.collib. Custom destinations remain external paths in the index, so portable catalogue export gathers their originals and rewrites only the archive's index copy.

Catalogue archives keep the existing ZIP format for small exports. A source above 40 MB or total above 256 MB uses the stored ZIP64 stream in Zip.swift; Sharing.inspect extracts and verifies each file without holding the photo payload in memory. New archive staging must be discarded after use. Source and destination trees should be reused when adding other object-asset adapters.

The separate **Add to Collection** panel sits between File Renaming and Destination. Its house checkbox enables a house dropdown of the active catalogue's user-created asset Collections; its header `+` creates a Collection. Import records every successfully added asset in the selected Collection within the same file transaction. A skipped file is not collected or marked seen. Membership lives in `CatalogueFile.assetCollections` inside the existing `.colcat`, independently of `SchemaCollection` ownership: a stable asset identity may belong to many Collections without moving or copying it.

Catalogue cleanup never deletes referenced originals. Explicit edits to an unlocked native palette write back to the source through the shared transaction, preserving its native identity and ownership. ## Shared edit ownership

`FileHandlers/Handler_File_Edit_Access.swift` owns the protocol. Native metadata uses `header.editControl`; other formats use the same structure in their `.colcar` header. The claim records process-session identity, user, machine and claim time. Only its owner can release it. The header state describes availability/claim; the UI padlock describes whether this session may edit.

Each claim/release and managed write checks ownership within an exclusive sibling `.colguard` directory. Shared file-manager native and raw writes enforce the gate; ASE append uses it too. Sidecar payload writes use the source's same guard. Normal termination releases this session's claims. Crashes retain claims/guards; recovery, expiry and administrator takeover are deliberately deferred. This is cooperative Colorgain coordination, not an OS access-control change or a lock honoured by unrelated software.

## Agreed history direction

Native assets and sidecars will retain full asset revision history. Restoring a historical state creates a new independent identity with `derivedFrom` asset/revision provenance; it never rewinds the shared original. The original retains its latest version and history. Binary assets need retained version data or reproducible non-destructive operations and a protected original; a textual log cannot restore overwritten pixels. The sidecar includes a history container, but revision capture, historical binary storage and the restore-as-copy UI are not implemented by the lock foundation.

## Native menu organisation

`main.swift` adds Catalogue, Assets and Metadata beside the existing menus. File keeps its established commands and shortcuts. Catalogue exposes management, schema, member creation, search, sync and export routes. Assets reuses shared import, creation, palette review and export operations. Metadata exposes the Tags page and selected-palette tag editor. Palette-specific actions name their scope and validate the currently displayed palette, including edit ownership. Unimplemented commands are disabled with a `! ` prefix; they must never claim success or create placeholder writes. Expand these through existing domain handlers as features become available.
